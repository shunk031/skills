# Gemini による日本語成果物の作成

すべての日本語成果物でこの手順に従う。PR や issue の本文・コメント、コミットメッセージ、Markdown 文書、レポート本文、投稿文、コードや HTML 内の日本語文字列が対象となる。日本語が含まれる成果物は日英併記を含め本手順の対象とする。本手順は日本語成果物のための手順であり、英語のみの文章やチャット返信は対象外とする。呼び出し元（Claude、Codex、Gemini）が自ら日本語を下書き・推敲せず agy に委託するのは、Gemini による文章品質の統一と執筆・レビューの客観的分離を徹底するためである。agy にシェル・コード実行権限を与えない（permissions.deny に command(*) を指定）のは、文章の作成・点検に専念させ、コマンド誤実行や副作用を防ぐためである。呼び出し元がこの分担を破って自ら下書きや修正を行った場合、必要な多段階品質ゲートを通過していない無効な出力となり、承認記録も行えず破棄または再執筆が必要となる。

## 執筆

1. 成果物のワークスペース内で出力先ファイルパスを定める。PR・issue 本文やコミットメッセージを含む全成果物をワークスペース内のファイルに下書きさせ、同一の承認済みファイルをレビュー、記録、公開でそのまま使用できるようにする。呼び出し元はその承認されたファイルをそのまま使用する責任を負う。呼び出し元は、レポート、wiki ページ、PR・issue 本文をはじめとする実質 4 行以上のあらゆる読者向け成果物を執筆する前に短いブリーフを作成する。実質 4 行を境界とするのは、単一の要約のみで構造を持たない極小の成果物にブリーフを課す過剰な負荷を避けつつ、複数論点や構成を伴う文書で論点脱落や論旨拡散を防ぐ実用的な基準とするためである。実質行数は表示上の折り返しではなく改行コードによる論理行で空行を除いて数え、完成した下書きでも実質行数を再確認する。下書きがブリーフなしで基準に達した場合は納品を阻止し、呼び出し元へ差し戻してブリーフ作成と確認を行わせたうえで執筆とレビューを最初からやり直す。1 行のコミットメッセージは単一の変更要約のみを伝え構造を持たないため明示的に免除され、実質 4 行未満の成果物も基準未満としてブリーフ作成の対象外とする。ブリーフには、想定読者、読者の判断または行動、論点の拡散や脱落を防ぐための必須の 3〜5 点（各点にはそれを含める理由ではなく、その論点を裏づける該当箇所の抜粋、事実、数値、コード、リンクなどの根拠・元資料の参照を明記）、意図的に除外する事項、従う構成、および確認状況を明記する。確認状況には「利用者が確認済み」または「利用者が応答不能」のいずれかを記録する。応答不能とは非対話環境などで確認を求める手段自体が存在しない状況を指し、対話セッションでの返答待ちは応答不能に当たらない。応答手段がない場合に限り応答不能として執筆を進めてよい。利用者が成果物の見出しや項目などの構成を指定済みの場合はそれを仕様とし、その枠を埋め、要求されていない節も並行する構成も追加してはならない。枠のない追加提案がある場合は列挙する。利用者が応答可能な場合は執筆前に利用者の確認を得る。利用者が応答可能であるにもかかわらず確認が得られていない場合、執筆を開始してはならない。未確認のブリーフを承認済みと表現してはならない。作成したブリーフは、免除対象外の成果物において執筆担当と内容レビュー担当の双方に渡す。呼び出し元は、読者が参照先を直接開いて検証できるように、チケット、issue、PR などの内部識別子のリンク先 URL を元資料（執筆の根拠となる事実、数値、コード、リンクの抜粋）に含める。執筆担当がファイル全体から誤解釈したり事実を創作したりするのを防ぐため、単なるファイルパスではなく該当する抜粋自体を元資料とする。
2. Herdr（ターミナルペインやエージェントセッションを管理する CLI）を使い、作業対象のワークスペース（`<workspace-id>`）に左右 2 ペイン構成の専用 agy（Gemini エージェントを起動する CLI）タブを作成して返されたタブ ID を保持し、タブのルートペイン（`<root-pane-id>`）で一意なエージェント名と構成の再現性を保つための本手順の標準モデル識別子 `gemini-3.8-flash-high` を指定して agy を起動する。`<workspace-id>` やペイン・タブ ID の CLI 応答フォーマットと ID の取り扱いは既存の `herdr` スキルを情報源として参照し、その CLI 手順を重複記述しない。起動時に現在のワークツリーを確認したうえで承認するプロジェクト信頼ダイアログ（workspace trust dialog）が表示された場合は応答し、入力コンポーザー（プロンプト入力欄）が準備完了するまで待ってからプロンプトを送信する。エージェント管理の詳細は `shunk031-herdr-orchestrate-workers` skill を参照する。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <writer-name> --kind agy --pane <root-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

3. agy に元資料と出力先パスを渡し、免除対象外の成果物ではブリーフも渡してそのファイルに日本語成果物を書かせる。免除対象外の成果物では、執筆着手前のブリーフ受領、必須項目と元資料の充足、および利用者が応答可能な場合の利用者確認を必須とする。agy は対話チャネルを持たず全体の進行管理は呼び出し元が担うため、これらが不足している場合は利用者に直接質問せず、執筆も行わずに呼び出し元へ差し戻す。免除対象の成果物はブリーフなしで執筆を進める。プロンプト送信後はプロンプトの脱落やハングを防ぐため、`shunk031-herdr-orchestrate-workers` skill の受領契約に従い、`herdr agent get` で得られるより新しい状態遷移番号（`state_change_seq`）と可読テキストを確認する。いずれかが欠けている場合は同一プロンプトを 1 回再送し、再送後も受領確認に失敗した場合はそのまま進めずに作業を停止して呼び出し元に報告する。執筆担当は提供された内部識別子のリンクを使い、読者向け説明はブリーフに従う。呼び出し元の Claude、Codex、Gemini は、日本語の下書きや書き換えを自分で行ってはならない。コードや HTML 内の日本語は、日本語文字列だけを編集させる。
   - 文体と執筆スキルの選択:
     - 執筆担当は `shunk031-writing-router` skill（文書目的に応じて担当スキルを選ぶスキル）に従って担当を選び、選んだスキルと必要な依存先だけを読んで適用する。利用者が文体、形式、スキルを指定している場合はその指定を優先する
     - 特定の文体をすべての成果物に一律強制してはならず、ルーターの基準と利用者の要求に従う
   - 長さ制限の遵守:
     - 冗長化や可読性低下を防ぐための固定上限方針に従う
     - 対象: 変更された Markdown（.md）ファイルと対応する gh PR・issue 本文の入力
     - 算定定義: 文末の句読点・約物および直後の閉じ引用符・閉じ括弧が文の境界を定義し、表示上の折り返しは文境界とみなさない。句読点等で終わらないリスト項目は 1 文として数える。カウントは書記素クラスタではなく、Python の str len() に相当する個別の Unicode コードポイント単位で行う
     - 文の検査（論理文をカウント）: 日本語文は最大 100 コードポイント、その他の文は最大 200 コードポイント
     - GitHub 本文ブロック（コード、HTML、表、URL を除く）: 各段落およびネストを含む全リスト項目で最大 600 コードポイント

## レビュー

1. 同じ専用タブ内で執筆担当のルートペイン（`<writer-pane-id>`）を右に分割し、単一の右ペイン（`<new-reviewer-pane-id>`）で新しい agy セッションを起動する。執筆担当のセッションを使い回すと執筆時の文脈やバイアスを引き継ぐため、必ず独立した新規セッションで客観的にレビューする。タブ構成を乱さずセッション管理の混乱を防ぐため、追加のペイン分割を行ってはならない。起動時にプロジェクト信頼ダイアログが表示された場合はワークツリーを確認して応答し、入力コンポーザーが表示上準備完了するまで待ってからプロンプトを送信する。内容レビュー担当に元資料と出力先ファイルパスを渡し、免除対象外の成果物ではブリーフも渡す。プロンプト送信後は毎回受領契約に従い、`herdr agent get` のより新しい `state_change_seq` と可読テキストを確認する。欠けている場合は 1 回再送し、再送後も受領確認に失敗した場合は作業を停止して呼び出し元に報告する。

   ```bash
   herdr pane split <writer-pane-id> --direction right --cwd "$PWD" --no-focus
   herdr agent start <reviewer-name> --kind agy --pane <new-reviewer-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

2. `shunk031-writing-router` で選ばれた執筆スキルに照らし、成果物を判定するよう内容レビュー担当に依頼する。レビュー担当は、事実、数値、リンク、コードが元資料と一致しているかを確認し、コードや HTML では日本語文字列だけが変更されているかも確認する。元資料にない内容を要求したり、ファイルを編集したりしてはならない。判定結果は指摘事項を添えた `ACCEPT` または `REJECT` で返させる。
   - ブリーフ不備・不整合は `REJECT`: 免除対象外の成果物でブリーフの欠落や必須項目の不足がある場合、利用者が応答可能であるにもかかわらず確認が得られていない場合、ブリーフに定めた必須事項（3〜5 点）の各点に裏づけ根拠があるか、また内容がブリーフに寄与しているかを確認し、必須事項の記述漏れや裏づけ不足がある場合、またはブリーフの想定読者や判断・行動に寄与しない記述、意図的除外事項の混入、指定構成からの逸脱がある出力
   - URL の不備は `REJECT`: 内部識別子のリンク先 URL が元資料にない場合、または元資料に裏づけのない URL を含む出力（フォールバック: 元資料に内部識別子のリンク先 URL が不足している場合は `REJECT` し、呼び出し元に提供を要求）
   - 文体規則の違反は `REJECT`: `shunk031-writing-router` で選ばれた担当スキルおよび利用者が指定した形式・文体の基準に反する出力
   - 長さ制限の違反は `REJECT`: スキル方針として定める固定制限値に違反した出力（文境界およびコードポイントの算定は執筆の定義に従う）
     - 対象: 変更された Markdown（.md）ファイルと対応する gh PR・issue 本文の入力
     - 文の検査（論理文をカウント）: 日本語文で 100、その他の文で 200 コードポイントを超過
     - GitHub 本文ブロック（コード、HTML、表、URL を除く）: 各段落またはネストを含む全リスト項目で 600 コードポイントを超過
   - 事実の裏づけ不足は `REJECT`: 元資料の不足または成果物の記述を裏づけられない出力
     - 対象: 成果物内の数値、用語定義や注釈、判定基準
     - フォールバック: 元資料が未提供、または提示された抜粋が成果物の数値、用語定義や注釈、判定基準を裏づけない場合は `REJECT` し、呼び出し元に該当箇所の抜粋提供を要求
     - 文書の事実を再記述する場合、呼び出し元は単なるファイルパスではなく該当する抜粋自体を渡す
     - 抜粋が成果物の記述と矛盾する場合は、単なる不足ではなく事実の不一致として `REJECT` し執筆担当に修正させる
3. `REJECT` の場合は、指摘事項と利用可能な元資料を執筆担当に送って修正させる。事実の裏づけ不足の指摘では、執筆担当に事実を創作させず、呼び出し元が再レビュー前に指摘とともに抜粋を執筆担当に提供する。再レビューのたびに同じ右ペインで前回のレビュー担当セッションを終了し、右ペインのシェルが準備完了になったことを確認してから、その右ペインで別の新規 agy セッションを起動して再レビューする。執筆担当のセッションを使い回したり、別のペインを分割したりしてはならない。差し戻しと修正の往復は、初読や初見レビューでの指摘修正も含めたすべての修正ループを合算して最大 2 回までとし、誰がレビューするかに関わらずこの上限を適用する（レビュー担当の変更やエスカレーションによってもリセットされない）。これは無限ループを防ぎ、未解決の根本課題を早期に利用者に報告するためである。2 回の修正・再レビューを経ても解決しない場合は作業を停止して残った指摘事項を報告し、納品してはならない。

   ```bash
   herdr agent send-keys <previous-reviewer-name> ctrl+c
   herdr agent start <new-reviewer-name> --kind agy --pane <reviewer-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

4. 執筆完了後・納品前に、ブリーフや元資料を渡さず完成文書のみを受け取る新規の初読者（既存スキル `first-reader`、参照先: `~/.agents/skills/first-reader/SKILL.md`）と、独立した初見レビュー（fresh-first-look review、判定基準は `shunk031-herdr-orchestrate-workers` の「Before handing any reader-facing artifact…」で始まる読者向け成果物レビュー節を参照）を実行する。いずれもペインを作成せず、`shunk031-herdr-orchestrate-workers` skill に従ってセッション内の新規サブエージェントとして実行する。ブリーフや元資料を渡さないのは、先行知識を持たない初見読者の体験を再現し、背景を知る者が見落としやすい説明不足や疑問を検出するためである。両者は参照先として再利用し、その手順やチェックリストを本スキルで再現・重複記述しない。`first-reader` skill からは「なぜ」「だから何」「これは何か」の疑問を報告させ（`first-reader` 自身は `ACCEPT` を判定しない）、`shunk031-herdr-orchestrate-workers` の初見レビューから明示的な `ACCEPT` が得られ、かつ `first-reader` からの未解決の疑問が一切ないことを合格条件とする。未解決の疑問や不備が見つかった場合はその指摘を執筆担当に差し戻して修正させ、修正後に内容レビューと新規サブエージェントによる初読・初見レビューをやり直す（ステップ 3 の合算 2 回の上限を適用）。合格条件を満たすまで納品してはならない。これらはブリーフと元資料を受け取る内容レビュー担当とは明確に分離する。
5. agy が未インストール、未認証、レート制限、またはオフラインで利用できない場合は、成果物を保留して利用者に伝える。`ACCEPT` なしで公開してはならない。
6. 承認記録の追記または成果物の保留を終えたら、この手順で開いたタブを `herdr tab close <tab-id>` で閉じる。呼び出し元や利用者が作業中の他の無関係なタブを誤って閉じないため、この手順で開いていないタブは決して閉じない。

   ```bash
   herdr tab close <tab-id>
   ```

## 承認の記録

内容レビュー担当の `ACCEPT`、初見レビューの明示的 `ACCEPT`、および初読者からの未解決疑問解消のすべてがそろった後に限り、呼び出し元がその結果を確認し、自分で次の単一シェルコマンドを実行して記録を 1 行追記する。ファイルパスは承認されたファイルの絶対パスに置き換える。

```bash
(
  set -o pipefail
  FILE="/absolute/path/to/accepted-file"
  [[ -f "$FILE" && -r "$FILE" ]] || exit 1
  HASH="$(perl -0777 -e '$_ = <STDIN> // ""; s/\r\n/\n/g; s/\n*\z/\n/; print' < "$FILE" | shasum -a 256 | cut -d ' ' -f 1)" || exit 1
  [[ "$HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
  STAMP="$(date -u +%Y-%m-%dT%H:%M:%SZ)" || exit 1
  mkdir -p "$HOME/.local/state/agy-japanese" || exit 1
  printf '%s\t%s\t%s\n' "$STAMP" "$HASH" "$FILE" >> "$HOME/.local/state/agy-japanese/accepted.tsv"
)
```

ユーザーごとの記録ファイルは `~/.local/state/agy-japanese/accepted.tsv` とする。タブ区切りの各行には、UTC タイムスタンプ、SHA-256、承認されたファイルのパスを記録する。この記録と SHA-256 はどの承認済みファイルが使用されたかを残す手動の監査記録であり、自動化されたゲートがこれを検査するわけではないため、呼び出し元が承認されたファイルを変更なくそのまま使用する責任を負う。ハッシュ計算前に CRLF を LF に正規化し、末尾の改行を 1 つの LF に整えるのは、OS やエディタによる改行差分を吸収し、同一内容から常に同一のハッシュを一貫して得るためである。以降の `gh`、コミット、アップロードの本文には承認されたファイルの内容をそのまま使う。少しでも編集した場合は、新しいレビューと記録をやり直す。
