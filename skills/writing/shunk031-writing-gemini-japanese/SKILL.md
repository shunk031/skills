# Gemini による日本語成果物の作成

呼び出し元（親エージェント）は、日本語成果物の執筆・編集・公開時に本スキルを使用し、自ら日本語を下書き・推敲・編集せず、ワーカーを起動して本手順を開始する。対象は、PR や issue の本文・コメント、コミットメッセージ、Markdown 文書、wiki、レポート本文、設計や調査のメモ、投稿文、コードや HTML 内の日本語文字列を含む、あらゆる読者向けの日本語成果物（日英併記を含む）とする。英語のみの文章や利用者へのチャット返信は対象外とする。ワーカー連携やオーケストレーションは `shunk031-herdr-orchestrate-workers` skill に従う。すべての agy（Gemini CLI）ワーカーはシェルコマンドを拒否する `permissions.deny` に `command(*)` を指定して起動する。ワーカーには日本語成果物の執筆またはレビューのみを行わせ、シェルコマンドを実行させず、プログラムコード自体を書かせない（コードや HTML 内の日本語文字列のみ編集可）。呼び出し元は各ワーカーのトランスクリプトで受領文（`✍️ 私は shunk031-writing-gemini-japanese を読みました。`）を確認してから作業を進め、確認できない場合は再送または再起動する。

## 準備とブリーフ

呼び出し元がワークスペース内の出力先ファイルパスを定める（コードや HTML は対象ファイルパスを指定）。

1. 対象判定: 読者向け文書には、レポート、wiki ページ、PR や issue の本文、複数段落の PR や issue コメント、設計や調査のメモ等が含まれる。これらのうち、新規に作成するもの、または構成を変更するものは、下書きの前にブリーフ作成を必須とする。免除されるのは、コミットメッセージ、単一段落の PR や issue コメント、コードや HTML 内の日本語文字列、および構成・読者・主張を変更しない既存文書への文単位の修正のみである。複数段落の PR や issue 本文・コメントは免除されない。判定基準は新規作成または構成変更の有無であり、行数や文字数を理由にブリーフ作成を回避してはならない。
2. ブリーフ作成: ブリーフは読者向け成果物ではなく作業指示であるため呼び出し元自身が作成し、その内容の責任を持つ。利用者が構成やアウトラインを指定した場合でもブリーフの全項目が必要である。ブリーフには以下を含める。
   - 想定読者
   - 読者の判断または行動
   - 根拠付き必須要件 3〜5 点（各要件を直接裏づける根拠資料を指定する。必須の個別事実が 5 点を超える場合は集約して 3〜5 点とする）
   - 意図的に除外する事項
   - 構成（利用者がすでに書いた構成がある場合はそれを唯一の仕様としてその枠のみを埋め、並行する構造を追加せず、枠のない追加事項はすべて列挙する。指定がない場合は呼び出し元が指定する）
3. ブリーフのレビュー: 呼び出し元は、レビューや再レビューのたびに作業に関与していない新しいレビュー担当を起動し、ブリーフ、利用者の依頼、根拠資料を渡す。レビュー担当は、手順 2 の全項目があること、指定された根拠資料が各必須要件を直接裏づけていること、利用者の構成指定があればそれに従っていることを確認する。根拠資料に直接の裏づけがない場合は手順 5 を適用し、裏づけはあるが無指定や誤指定の場合は通常の修正往復とする。ACCEPT を得たブリーフをレビュー済みブリーフと呼び、この ACCEPT を得る前に下書きを開始してはならない。REJECT 時は呼び出し元がブリーフを修正し、初回のレビュー後最大 2 回まで再レビューを受け、未解決なら作業を保留して利用者に報告する。
4. 共有: 呼び出し元はレビュー済みブリーフを執筆担当と内容レビュー担当の双方に渡す。
5. 根拠不足時の停止: 必須要件を直接裏づける根拠資料が不足している場合は、下書き・レビュー・納品を直ちに停止し、利用者に資料提供を求める。必須要件の根拠を捏造したり、利用者の許可なく要件を省略したりしてはならない。利用者が資料を提供したか要件の省略に同意した後は、呼び出し元がブリーフを更新して手順 3 のレビューを再度受ける。この再レビューから新しく最大 2 回の往復を数え、利用者が省略に同意した場合は必須要件が 3 点未満になってもよい。

## 執筆

1. 執筆ワーカー起動: ブリーフの ACCEPT 後（免除対象では出力先ファイルパス決定後）、専用タブを作成して agy 執筆担当ワーカーを起動する。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <writer-name> --kind agy --pane <root-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

   起動時の project trust や hooks review のすべての判断は例外を含め `shunk031-herdr-orchestrate-workers` の手順 4 に従う。入力欄（composer）が利用可能になるまで待ってからプロンプトを送信する。各プロンプト送信後は `shunk031-herdr-orchestrate-workers` の手順 5 に従い、新しい `state_change_seq` および可読な送受信テキストを確認する。いずれかが欠けている場合は同じプロンプトを 1 回だけ再送する。

2. 下書き作成: 成果物はすべてワークスペース内のファイルに出力させる（コードや HTML では対象ファイル内の日本語文字列のみを編集）。元資料、出力先パス、および要ブリーフ文書ではレビュー済みブリーフを渡して執筆させる。要ブリーフ文書ではレビュー済みブリーフの指定に従い、必須要件を直接裏づける根拠を完成文書内に反映させる。すべての事実や数値は元資料の裏づけを要する。執筆担当は `shunk031-writing-router` skill に従って担当スキルを選定・適用する（利用者の指定がある場合は優先）。本人名義の文書では過去の同種文書とチームの作例を読む。全主張を本人の作業実績や明示の判断に結びつける。作業実績や明示の判断に辿れない内容は提案とするか除外する。

3. 共通チェックリスト: 執筆担当は以下の項目を適用する。初読者は全項目を検証し行ごとに報告する（指摘ゼロも含む）。

   - 用語: 読者が専門用語や造語を認識できるか確認すること。
   - 否定表現: 不要に安心させる否定表現がないこと。
   - 分量: 同種の先行文書や周囲の長さと整合していること。
   - 根拠: 裏づけのない主張や事実の捏造がないこと。
   - 構造: 箇条書き各項に 1 段字下げした平易な説明を 1 つだけ添えること。
   - 表現: 「〜の確立」や「〜による〜の実証」等の抽象名詞句がないこと。

4. 部分編集: 隣接箇所が箇条書きか地の文かとその階層の深さを記録する。文と箇条書きの文字数の中央値と最大値を計測する。ブリーフに各数値を明記し形式を揃える。各新設文と各箇条書きを対応する隣接中央値以下に抑える。検査には `markdown-sentence-length` を実行する。別 PR で作成中の `markdown-neighbor-length` も走らせる。

## レビュー

1. 内容レビュー: レビュー担当は専用タブを作成して新しい agy セッションを起動する。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <reviewer-name> --kind agy --pane <root-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

   起動確認およびプロンプト検証は執筆担当と同様に行う。元資料、出力先パス、文体規則、および要ブリーフ文書ではレビュー済みブリーフを渡す。レビュー担当はファイルを編集せず、指摘事項を添えた `ACCEPT` または `REJECT` を返す。次のいずれかに該当する場合は `REJECT` とする。

   - ブリーフ不整合: 要ブリーフ文書でのブリーフの欠落・未レビュー、ブリーフに奉仕しない内容、必須要件の欠落、除外事項の混入、指定構成からの逸脱
   - 根拠・裏づけ不足: 必須要件や事実・数値の直接の裏づけ不足、捏造
   - 形式・文体規則違反: 指定された形式や文体規則（`shunk031-writing-router` 等）への違反
   - 内部識別子リンクの不備: 成果物内の内部識別子（チケット、issue、PR 等の ID）に検証可能なリンクがない、照合できない、またはリンクのない内部識別子が含まれる場合（リンクのない内部識別子は納品不可）
   - 長さ制限違反: 変更された Markdown の各文が日本語 100 Unicode コードポイントまたはその他 200 Unicode コードポイントを超えている場合、あるいは PR や issue 本文の各段落および各リスト項目がコード、コードブロック、HTML、表、URL スパンを除いて 600 Unicode コードポイントを超えている場合（レビュー担当は違反を必ず REJECT とする）

2. 納品前ブラインドレビュー: 要ブリーフ文書に限り、内容レビューの `ACCEPT` 後にブラインドの初読者レビューを実施する。初読者レビューと初見レビューのどちらにもブリーフや元資料を渡さず完成文書のみを渡す。初読者は why / so what / what is this の疑問をすべて列挙し、文書内で回答されていない未解決の疑問が 1 つでもあれば納品を止める。初読者検証の手法は `first-reader` skill を参照し、全疑問の解消を必須とする。初見レビューのオーケストレーションは `shunk031-herdr-orchestrate-workers` skill を参照し、明示的な `ACCEPT` を必須とする。初読者は共通チェックリストの全項目を確認する。指摘ゼロの項目も含めて行ごとに対処を報告する。部分編集では隣接箇所と見比べ形式や長さを照合する。形式や長さの不整合があれば REJECT とする。呼び出し元は納品前に同様の比較を再度行う。
3. 修正と再レビュー: 内容レビューの `REJECT`、初読者の未解決の疑問、または初見レビューの `REJECT` が発生した場合は、指摘事項を執筆担当ワーカーに返して修正させ、修正後に必要なレビューをやり直す。再修正の前に変更対象の文を過不足なく列挙する。その修正範囲を列挙した文のみに限定する。修正・再レビューの往復は最大 2 回までとし、解決しない場合は納品を保留して利用者に報告する。

## 納品

すべての成果物で内容レビューの `ACCEPT` を得て、要ブリーフ文書ではレビュー済みブリーフ、初読者レビューの全疑問解消、および初見レビューの `ACCEPT` をそろえる。呼び出し元は最終文書を利用者に納品するか、利用者が明示的に指定した宛先のみに反映する。タスク PR やタスクブランチがあるタスクでは、タスクの依頼をもってそれらを宛先として指定したものとみなす。通常進行中、呼び出し元はブリーフ、下書き、レビューの往復を利用者に見せない。ただし各保留点からの保留報告では、例外としてブリーフや未解決の指摘事項を提示できる。要求されていない公開を行ってはならない。

1. 承認記録: 冒頭の全納品条件を満たした後、呼び出し元は `FILE` を承認ファイルの絶対パスに置き換えて以下のコマンドを実行する。`~/.local/state/agy-japanese/accepted.tsv` に UTC タイムスタンプ、SHA-256、ファイルパスを記録する。

   ```bash
   (
     set -o pipefail
     FILE="/absolute/path/to/accepted-file"
     [[ -f "$FILE" && -r "$FILE" ]] || exit 1
     HASH="$(perl -0777 -e '$_ = <STDIN> // ""; s/\r\n/\n/g; s/\n*\z/\n/; print' < "$FILE" | shasum -a 256 | cut -d ' ' -f 1)" || exit 1
     [[ "$HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
     STAMP="$(date -u +%Y-%m-%dT%H:%M:%SZ)" || exit 1
     mkdir -p "$HOME/.local/state/agy-japanese" || exit 1
     printf '%s\t%s\t%s\n' "$STAMP" "$HASH" "$FILE" >> "$HOME/.local/state/agy-japanese/accepted.tsv"
   )
   ```

2. 納品: 成果物を利用者に納品する場合は、完成文書の引き渡しをもって唯一の確認とする。タスク外の他者向け投稿やコメント、issue 本文、タスクブランチ外への push など、タスク外へ反映する宛先には、反映直前に 1 回だけ最終確認を求める。その確認では、リンクがある場合はリンクと完成テキストを提示する。呼び出し元自身のタスク PR 本文やその PR へのコメント、タスクブランチ上のコミットメッセージは、タスク依頼で宛先に指定されたとみなされるため個別の確認を要しない。コードや HTML 内の日本語文字列は対象ファイル内での編集をもって納品とするため、個別の確認を要しない。その他の成果物は、承認されたファイルの内容を無変更のまま要求された宛先（`gh` の本文オプション、コミットメッセージ等）に反映する。内容を変更した場合や、納品時・最終確認時に利用者が変更を求めた場合は執筆担当ワーカーが修正する。変更がブリーフ（必須要件、除外事項、構成）に及ぶ場合は呼び出し元が更新し、準備とブリーフの手順 3 の再レビューを新しい 2 回の上限で先に受ける。その後は内容レビューから再開し、レビュー手順 3 の修正往復を新しく最大 2 回まで数える。再レビュー完了後、最終確認を要していた宛先に限り改めて 1 回だけ最終確認を行う。上限に達した場合は作業を保留して利用者に報告する。
3. レビュー不達時の保留: agy が利用できない場合、または必要なレビューや根拠資料が欠けている場合は、成果物を保留して利用者に報告し、親エージェントによる代行などの未承認手段で納品・公開してはならない。
4. タブの終了: 納品完了後または保留後、呼び出し元は本手順で開いた各タブを閉じる。本手順で開いていないタブは閉じない。
