# Gemini による日本語成果物の作成

すべての日本語成果物でこの手順に必ず従う。PR と issue の本文・コメント、コミットメッセージ、Markdown 文書、レポート本文、投稿文、コードや HTML 内の日本語文字列が対象になる。チャット返信と英語の成果物は対象外とする。

## 執筆

1. 成果物のワークスペースで、元資料と出力先ファイルパスをそろえる。必要な事実、数値、リンク、コード、骨子、下書きを執筆担当に渡し、不足している情報を創作させない。読み手に行動を求める成果物（フォーム、レビューシート、指示・手順書など）では、呼び出し元は想定する読み手、利用端末（例: スマホ）、完了すべき作業も元資料に含める。
2. そのワークスペースに左右 2 ペイン構成の専用 agy タブを作成して返されたタブ ID を保持し、タブのルートペインで一意なエージェント名と必須モデルを指定して agy を起動する。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <writer-name> --kind agy --pane <root-pane-id> -- --model gemini-3.8-flash-high
   ```

3. agy に元資料と出力先パスを渡し、そのファイルに日本語成果物を書かせる。必要な情報が不足している場合、執筆担当は質問してよい。呼び出し元の Claude、Codex、Gemini は、日本語の下書きや書き換えを自分で行ってはならない。コードや HTML 内の日本語は、日本語文字列だけを編集させる。
   - 日本語成果物の既定文体は骨子箇条書き → テレグラフ短縮 → natural-japanese による推敲に固定する
     - 対象: レポート / PR・issue の本文とコメント / メモ / README などの Markdown 文書 / コミットメッセージ
     - 事前読込: 執筆担当は執筆前に `~/.agents/skills/shunk031-writing-kosshi/SKILL.md`、`~/.agents/skills/shunk031-writing-telegraph/SKILL.md`、`~/.agents/skills/natural-japanese/SKILL.md` をこの順序で読み、その順序で適用
     - 手順: `shunk031-writing-kosshi` で骨子箇条書きを作成 → `shunk031-writing-telegraph` で短縮 → `natural-japanese` で AI らしい表現や翻訳調を推敲
     - 形式維持: `natural-japanese` による推敲時も骨子階層とテレグラフの 1 行 1 項目を維持
     - セクション構造: 先頭に主張 1 行 → 根拠を 1 段下に配置
     - 行の粒度: 1 行 1 項目
     - 語句の圧縮: 文脈から自明な語を省略
     - 記号: 関係に応じて `→` / `➜` / `vs.` / `:` / `/` を使用
   - 呼び出し元が段落文章を明示した場合だけ例外とする
     - 対象例: ブログ記事などの段落文章
     - 文体選択: `shunk031-writing-router` を使用
     - 指示条件: 呼び出し元が執筆担当への指示に段落文章の要求を明記
   - フックの長さ制限を遵守する
     - 対象: 変更された Markdown（.md）ファイルと対応する gh PR・issue 本文の入力
     - 文の検査（表示行ではなく変更された Markdown の文をカウント）: 日本語文は最大 100 Unicode コードポイント、その他の文は最大 200 Unicode コードポイント
     - GitHub 本文ブロック（コード、コードブロック、HTML、表、URL スパンを除く）: 各段落およびネストを含む全リスト項目で最大 600 Unicode コードポイント

## レビュー

1. 同じ専用タブ内で執筆担当のルートペインを右に分割し、単一の右ペインで新しい agy セッションを起動する。執筆担当のセッションをレビューに使い回してはならず、別のペインをさらに分割してもならない。レビュー担当に元資料と出力先ファイルパスを渡す。

   ```bash
   herdr pane split <writer-pane-id> --direction right --cwd "$PWD" --no-focus
   herdr agent start <reviewer-name> --kind agy --pane <new-reviewer-pane-id> -- --model gemini-3.8-flash-high
   ```

2. `~/.gemini/config/skills.json` 経由で `~/.agents/skills` から読み込まれる既存の執筆スキルに照らして、成果物を判定するようレビュー担当に依頼する。レビュー担当は、事実、数値、リンク、コード、`<!-- -->` プレースホルダーが元資料と一致しているかを確認し、コードや HTML では日本語文字列だけが変更されているかも確認する。元資料にない内容を要求したり、ファイルを編集したりしてはならない。判定結果は指摘事項を添えた `ACCEPT` または `REJECT` で返させる。
   - 既定文体のレビューでは `shunk031-writing-kosshi` の階層、`shunk031-writing-telegraph` の行形式と短縮、`natural-japanese` を明示的に検査する
     - 平板な主張・根拠階層は `REJECT`: 主張と根拠が同じ階層
     - 複数項目の混在は `REJECT`: 1 行に複数項目
     - 長文の残存は `REJECT`: 短縮されていない長い文
     - 平板な並行箇条書きは `REJECT`: `shunk031-writing-telegraph` の「表」の規則に反し、表またはグループ化すべき並行項目
     - 不自然・翻訳調の残存は `REJECT`: AI らしい表現や翻訳調の言い回し
     - 段落文章の例外指定時: 指定された文体スキルの基準で判定
   - 長さ制限の違反は `REJECT`: フックの検査対象と制限に違反した出力
     - 対象: 変更された Markdown（.md）ファイルと対応する gh PR・issue 本文の入力
     - 文の検査（表示行ではなく変更された Markdown の文をカウント）: 日本語文で 100、その他の文で 200 Unicode コードポイントを超過
     - GitHub 本文ブロック（コード、コードブロック、HTML、表、URL スパンを除く）: 各段落またはネストを含む全リスト項目で 600 Unicode コードポイントを超過
   - 読み手への説明不足は `REJECT`: 指定された読み手と作業に対し、行動に必要な説明が不足した出力
     - 対象: 成果物内で読み手が行動すべき用語・ラベル・節
     - 判定基準: それが何か・なぜあるか・どう扱うかの説明不足を列挙（元資料にない事実の要求には当たらず、呼び出し元が補うべき説明不足として報告）
     - フォールバック: 読み手に行動を求める成果物の元資料に想定読者や作業の指定がない場合は `REJECT` し、呼び出し元にそれらの提供を要求
   - 事実の裏づけ不足は `REJECT`: 元資料の不足または成果物の記述を裏づけられない出力
     - 対象: 成果物内の数値、用語定義や注釈、判定基準
     - フォールバック: 元資料が未提供、または提示された抜粋が成果物の数値、用語定義や注釈、判定基準を裏づけない場合は `REJECT` し、呼び出し元に該当箇所の抜粋提供を要求
     - 文書の事実を再記述する場合、呼び出し元は単なるファイルパスではなく該当する抜粋自体を渡す
     - 抜粋が成果物の記述と矛盾する場合は、単なる不足ではなく事実の不一致として `REJECT` し執筆担当に修正させる
3. `REJECT` の場合は、指摘事項と利用可能な元資料を執筆担当に送って修正させる。説明不足の指摘では、執筆担当に事実を創作させず、呼び出し元が指摘とともに必要な事実を執筆担当に提供する。事実の裏づけ不足の指摘でも同様に、呼び出し元が再レビュー前に指摘とともに抜粋を執筆担当に提供する。再レビューのたびに同じ右ペインで前回のレビュー担当セッションを終了し、右ペインのシェルが準備完了になったことを確認してから、その右ペインで別の新規 agy セッションを起動して再レビューする。執筆担当のセッションを使い回したり、別のペインを分割したりしてはならない。差し戻しと修正の往復は最大 2 回までとする。2 回目のレビューでも却下された場合は作業を止め、残った指摘事項を利用者に示す。

   ```bash
   herdr agent send-keys <previous-reviewer-name> ctrl+c
   herdr agent start <new-reviewer-name> --kind agy --pane <reviewer-pane-id> -- --model gemini-3.8-flash-high
   ```

   - エスカレーション: 呼び出し元が出力の誤りや質の低さを判断した場合、または Flash のレビュー担当が明らかな問題を見落とした場合は、必要に応じて執筆担当やレビュー担当に `gemini-4-argon-high` を使い、該当工程をやり直す

4. agy が未インストール、未認証、レート制限、またはオフラインで利用できない場合は、成果物を保留して利用者に伝える。`ACCEPT` なしで公開してはならない。
5. 承認記録の追記または成果物の保留を終えたら、この手順で開いたタブを `herdr tab close <tab-id>` で閉じる。この手順で開いていないタブは決して閉じない。

   ```bash
   herdr tab close <tab-id>
   ```

## 承認の記録

新規レビュー担当が `ACCEPT` を返した後に限り、そのレビュー担当に次の単一シェルコマンドで記録を 1 行追記させる。ファイルパスは承認されたファイルの絶対パスに置き換える。

```bash
(
  set -o pipefail
  FILE="/absolute/path/to/accepted-file"
  [[ -f "$FILE" && -r "$FILE" ]] || exit 1
  HASH="$(perl -0777 -e '$_ = <STDIN> // ""; s/\r\n/\n/g; s/\n*\z/\n/; print' < "$FILE" | shasum -a 256 | cut -d ' ' -f 1)" || exit 1
  [[ "$HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
  STAMP="$(date -u +%Y-%m-%dT%H:%M:%SZ)" || exit 1
  mkdir -p "$HOME/.local/state/agy-japanese" || exit 1
  printf '%s\t%s\t%s\n' "$STAMP" "$HASH" "$FILE" >> "$HOME/.local/state/agy-japanese/accepted.tsv"
)
```

ユーザーごとの記録ファイルは `~/.local/state/agy-japanese/accepted.tsv` とする。タブ区切りの各行には、UTC タイムスタンプ、SHA-256、承認されたファイルのパスを記録する。ハッシュ計算の前に CRLF を LF に正規化し、末尾の LF バイトをすべて除去したうえで末尾に LF を 1 つだけ付与する。以降の `gh`、コミット、アップロードの本文には承認されたファイルの内容をそのまま使う。少しでも編集した場合は、新しいレビューと記録をやり直す。
