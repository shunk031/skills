# Gemini による日本語成果物の作成

呼び出し元（親エージェント）は、公開または外部読者向けの日本語成果物の執筆・編集・公開時に本スキルを使用し、自ら日本語を下書き・推敲・編集せず、ワーカーを起動して本手順を開始する。対象は、PR や issue の本文・コメント、コミットメッセージ、Markdown 文書、wiki、レポート本文、設計や調査のメモ、投稿文、コードや HTML 内の日本語文字列を含む、外部読者向けの日本語成果物（日英併記を含む）とする。英語のみの文章、利用者へのチャット返信、およびエージェント間やオーケストレーター間（meta や root あての進捗・状況報告など）の内輪の文書は対象外とする。内輪の文書に対しては、書き方や文体を理由にした確認・承認を要求しない。ワーカー連携やオーケストレーションは `shunk031-herdr-orchestrate-workers` skill に従う。すべての agy（Gemini CLI）ワーカーはシェルコマンドを拒否する `permissions.deny` に `command(*)` を指定して起動する。ワーカーには日本語成果物の執筆またはレビューのみを行わせ、シェルコマンドを実行させず、プログラムコード自体を書かせない（コードや HTML 内の日本語文字列のみ編集可）。呼び出し元は各ワーカーのトランスクリプトで受領文（`✍️ 私は shunk031-writing-gemini-japanese を読みました。`）を確認してから作業を進め、確認できない場合は再送または再起動する。

## 準備とブリーフ

呼び出し元がワークスペース内の出力先ファイルパスを定める（コードや HTML は対象ファイルパスを指定）。

1. 対象判定: 読者向け文書には、レポート、wiki ページ、PR や issue の本文、複数段落の PR や issue コメント、設計や調査のメモ等が含まれる。エージェント間やオーケストレーター間（meta や root あてなど）の内部報告や進捗・状況報告などの内輪の文書は対象外であり、ブリーフ作成や書き方を理由にした確認・承認を要求しない。公開または外部読者向け文書のうち、新規に作成するもの、または構成を変更するものは、下書きの前にブリーフ作成を必須とする。免除されるのは、コミットメッセージ、単一段落の PR や issue コメント、コードや HTML 内の日本語文字列、および構成・読者・主張を変更しない既存文書への文単位の修正のみである。複数段落の PR や issue 本文・コメントは免除されない。判定基準は新規作成または構成変更の有無であり、行数や文字数を理由にブリーフ作成を回避してはならない。
2. ブリーフ作成と作業用利用: ブリーフは公開成果物ではなく執筆準備のための内部作業資料であるため、呼び出し元自身が作成して執筆担当に作業用として渡す。別の確認役によるブリーフのレビューや承認ゲート（ACCEPT を下書き開始条件とする手順）は設けない。公開成果物に対する確認役は最終文書の 1 人のみとし、必須要件や事実の直接の裏づけは最終文書の確認役が確認する。利用者が構成やアウトラインを指定した場合でもブリーフの全項目が必要である。ブリーフには以下を含める。
   - 想定読者
   - 読者の判断または行動
   - 根拠付き必須要件 3〜5 点（各要件を直接裏づける根拠資料を指定する。必須の個別事実が 5 点を超える場合は集約して 3〜5 点とする）
   - 意図的に除外する事項
   - 構成（利用者がすでに書いた構成がある場合はそれを唯一の仕様としてその枠のみを埋め、並行する構造を追加せず、枠のない追加事項はすべて列挙する。指定がない場合は呼び出し元が指定する）
3. 根拠不足時の停止: 必須要件を直接裏づける根拠資料が不足している場合は、下書き・納品を直ちに停止し、利用者に資料提供を求める。必須要件の根拠を捏造したり、利用者の許可なく要件を省略したりしてはならない。利用者が資料を提供したか要件の省略に同意した後は、呼び出し元がブリーフを更新して執筆を進める（利用者が省略に同意した場合は必須要件が 3 点未満になってもよい）。

## 執筆

1. 執筆ワーカー起動: ブリーフ作成後（免除対象では出力先ファイルパス決定後）、専用タブを作成して agy 執筆担当ワーカーを起動する。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <writer-name> --kind agy --pane <root-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

   起動時の project trust や hooks review のすべての判断は例外を含め `shunk031-herdr-orchestrate-workers` の手順 4 に従う。入力欄（composer）が利用可能になるまで待ってからプロンプトを送信する。各プロンプト送信後は `shunk031-herdr-orchestrate-workers` の手順 5 に従い、新しい `state_change_seq` および可読な送受信テキストを確認する。いずれかが欠けている場合は同じプロンプトを 1 回だけ再送する。

2. 下書き作成: 成果物はすべてワークスペース内のファイルに出力させる（コードや HTML では対象ファイル内の日本語文字列のみを編集）。元資料、出力先パス、および要ブリーフ文書ではブリーフを作業用資料として渡して執筆させる。要ブリーフ文書ではブリーフの指定に従い、必須要件を直接裏づける根拠を完成文書内に反映させる。すべての事実や数値は元資料の裏づけを要する。執筆担当は `shunk031-writing-router` skill に従って担当スキルを選定・適用する（利用者の指定がある場合は優先）。本人名義の文書では過去の同種文書とチームの作例を読む。全主張を本人の作業実績や明示の判断に結びつける。作業実績や明示の判断に辿れない内容は提案とするか除外する。

   成果物が目標・OKR シートの場合は、執筆担当は下書き前に [references/goal-sheets.md](references/goal-sheets.md) を読む。

3. 共通チェックリスト: 執筆担当は以下の項目を適用し、読者に誤解を与えない表現に整える。

   - 読者に伝わる表現にすること。
     - 専門用語や造語が読者に伝わるか確認すること。
     - 不要に安心させる否定表現を避けること。
     - 「〜の確立」や「〜による〜の実証」等の抽象名詞句を避けること。
   - 本人の語彙と意図を保つこと。
     - 裏づけのない主張や事実を足さないこと。
     - 例: `Before「案 A を実施する」→After「案 A を試してみたい」`のように、本人の語彙・固有名詞・希望の強さを保つこと。
     - 例: `Before「案内して利用を増やす」→After「利用を増やしたい」`のように、書かれていない手段や理由を足さないこと。
     - 例: `Before「割合は 5%」→After「割合は 5%?」`のように、未確定値を確定しないこと。
   - 節の役割に合わせること。
     - 例: `Before「背景も列挙」→After「必要な条件だけ」`のように、題名・隣接節から役割を定め、その役割に必要な内容だけを書くこと。
   - 箇条書きの分量と階層を隣接節に合わせること。
     - 隣接節に合わせ、親は 1 主張・目安 4 つ以内にすること。
     - 同種の先行文書や周囲の長さと整合させること。
     - 例: `Before「隣接節は 2 親項目＋詳細、対象節は 8 項目」→After「同じ 2 親項目＋詳細」`のように、長い同階層一覧を避け、詳細を字下げした子項目に分けること。
     - 主張・根拠の構成は [`shunk031-writing-kosshi`](../shunk031-writing-kosshi/) skill を参照すること。

4. 部分編集: 隣接箇所が箇条書きか地の文かとその階層の深さを記録する。文と箇条書きの文字数の中央値と最大値を計測し、形式を揃える。文長制限や近傍長など機械で扱える規則は、`markdown-sentence-length` や `markdown-neighbor-length` 等のツールによる機械補正および機械検査に回し、内容レビューの停止条件には含めない。

## レビュー

公開する日本語文書の確認は、確認役 1 人による内容確認と機械検査のみとし、内輪の文書（meta や root あての報告など）は確認ゲートを通さない。

1. 検査責務の分離と内容確認: 書式、表記、リンク形式、文長制限など機械で検査・修正可能な条件はツールや linter による自動検査に任せ、機械的に修正・検証する。内容確認は専用タブを作成して起動した 1 人の確認役のみが最終文書に対して行い、ブリーフを独立した確認関門としない（複数の確認役や初読者・初見レビューなどの追加レビュアーを重ねて起動しない）。

   ```bash
   herdr tab create --workspace <workspace-id> --label "✍️ agy" --no-focus
   herdr agent start <reviewer-name> --kind agy --pane <root-pane-id> -- --settings '{"permissions":{"deny":["command(*)"]}}' --model gemini-3.8-flash-high
   ```

   起動確認およびプロンプト検証は執筆担当と同様に行う。元資料、出力先パス、文体規則、および要ブリーフ文書では作業用ブリーフを参考資料として渡す。確認役はファイルを編集せず、指摘事項を添えた `ACCEPT` または `REJECT` を返す。確認役は、事実の誤りと、読者が意味を取り違える具体的な箇所（何が問題でなぜ修正が必要かが分かる what / why を伴う具体的な指摘）のみをブロッキングな指摘（`REJECT`）とする。根拠資料の確認は実質的な事実誤りを特定するための証拠として用いるが、裏づけ不足それ自体は停止理由（`REJECT`）とせず、事実誤りや具体的誤解が示されていない裏づけ不足の記述は非ブロッキング（advisory）とする。本人名義の文書であっても、文体や「本人らしさ」など主観的な好みだけを理由にした指摘は非ブロッキング（advisory）とし、停止理由（`REJECT`）にしない。書式、表記、リンク形式、文長制限、近傍長など機械で検査・修正できる条件は機械に任せ、内容レビューの停止条件に含めず、個人の好みやニット（nit）は非ブロッキング（advisory）とする。これは Google レビュアー基準（nit を非ブロッキングとし what/why を明記する）、Codex 基準（差分が導入した具体的・実用的な問題に対象を絞り nit を除く）、Copilot 基準（PR タイトル・本文やリポジトリ指示をレビュー文脈に含める）の知見に基づく。これらの根拠はレビュー調査報告にある一次資料の範囲を超えて一般化せず、技術コードレビューと日本語文書レビューの違いを保ち、文書としての実質的な事実誤りと読者の具体的誤解の防止に焦点を絞る。次のいずれかに該当する場合のみ `REJECT` とする。

   - 実質的な事実誤り: 捏造や事実・数値の誤りなど、実質的な事実誤り（根拠資料の確認は事実誤りを特定する証拠として用い、事実誤りや具体的誤解が示されていない単なる裏づけ不足の記述は非ブロッキングとする）
   - 読者の具体的誤解: 読者が文章の意味を取り違える具体的な箇所（何が問題でなぜ修正が必要かが分かる what / why を伴う具体的な指摘）

   成果物が目標・OKR シートの場合は、確認役は [references/goal-sheets.md](references/goal-sheets.md) を読む。

2. 修正と再確認: 内容確認で `REJECT` が発生した場合は、指摘事項を執筆担当ワーカーに返して修正させる。修正範囲は指摘された箇所に限定する。修正後は、最初の確認役が自身の指摘の解消のみを確認する。別の確認役を新たに起動せず、全文を再読して新しい指摘を探さない。機械検査は修正変更後に再実行する。修正・再確認の往復は最大 2 回までとし、解決しない場合は納品を保留して利用者に報告する。

## 納品

公開する日本語文書の納品条件は、機械検査の通過と、最終文書に対する 1 人の内容確認者による `ACCEPT`（事実誤りと読み手の誤解の解消）とする。内輪の文書（meta や root あての報告など）は確認ゲートを通さずそのまま進行する。ブリーフは内部作業資料であるためレビューや承認をそろえる必要はない。初読者レビューや初見レビューなど追加の確認役による承認は求めない。オーケストレーター（呼び出し元）は、依頼された範囲への適合と機械検査結果を確認するのみとし、全文を独立して再確認したり、全行をチェックリストで再点検したり、内容確認役を追加したり、別名の最終確認ゲートを残したりしてはならない。呼び出し元は最終文書を利用者に納品するか、利用者が明示的に指定した宛先のみに反映する。タスク PR やタスクブランチがあるタスクでは、タスクの依頼をもってそれらを宛先として指定したものとみなす。通常進行中、呼び出し元はブリーフ、下書き、レビューの往復を利用者に見せない。ただし各保留点からの保留報告では、例外としてブリーフや未解決の指摘事項を提示できる。要求されていない公開を行ってはならない。

1. 承認記録: 冒頭の全納品条件を満たした後、呼び出し元は `FILE` を承認ファイルの絶対パスに置き換えて以下のコマンドを実行する。`~/.local/state/agy-japanese/accepted.tsv` に UTC タイムスタンプ、SHA-256、ファイルパスを記録する。

   ```bash
   (
     set -o pipefail
     FILE="/absolute/path/to/accepted-file"
     [[ -f "$FILE" && -r "$FILE" ]] || exit 1
     HASH="$(perl -0777 -e '$_ = <STDIN> // ""; s/\r\n/\n/g; s/\n*\z/\n/; print' < "$FILE" | shasum -a 256 | cut -d ' ' -f 1)" || exit 1
     [[ "$HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
     STAMP="$(date -u +%Y-%m-%dT%H:%M:%SZ)" || exit 1
     mkdir -p "$HOME/.local/state/agy-japanese" || exit 1
     printf '%s\t%s\t%s\n' "$STAMP" "$HASH" "$FILE" >> "$HOME/.local/state/agy-japanese/accepted.tsv"
   )
   ```

2. 納品: 成果物を利用者に納品する場合は、完成文書の引き渡しをもって唯一の確認とする。タスク外の他者向け投稿やコメント、issue 本文、タスクブランチ外への push など、タスク外へ反映する宛先には、反映直前に 1 回だけ最終確認を求める。その確認では、リンクがある場合はリンクと完成テキストを提示する。呼び出し元自身のタスク PR 本文やその PR へのコメント、タスクブランチ上のコミットメッセージは、タスク依頼で宛先に指定されたとみなされるため個別の確認を要しない。コードや HTML 内の日本語文字列は対象ファイル内での編集をもって納品とするため、個別の確認を要しない。その他の成果物は、承認されたファイルの内容を無変更のまま要求された宛先（`gh` の本文オプション、コミットメッセージ等）に反映する。内容を変更した場合や、納品時・最終確認時に利用者が変更を求めた場合は執筆担当ワーカーが修正する。変更がブリーフ（必須要件、除外事項、構成）に及ぶ場合は呼び出し元が作業用ブリーフを更新して執筆担当ワーカーに渡し、修正後に内容確認から再開して修正往復を新しく最大 2 回まで数える（最初の確認役が自身の指摘解消のみを確認する）。再確認完了後、最終確認を要していた宛先に限り改めて 1 回だけ最終確認を行う。上限に達した場合は作業を保留して利用者に報告する。
3. レビュー不達時の保留: agy が利用できない場合、または必要なレビューや根拠資料が欠けている場合は、成果物を保留して利用者に報告し、親エージェントによる代行などの未承認手段で納品・公開してはならない。
4. タブの終了: 納品完了後または保留後、呼び出し元は本手順で開いた各タブを閉じる。本手順で開いていないタブは閉じない。

## レビュー返信・再レビュー依頼

レビューへの返信や再レビュー依頼のコメントを作成する際は、以下の規則を適用する。執筆担当は共通チェックリストとあわせて適用し、内容レビューでも確認する。

1. 変更点への集中: レビュー担当者が判断すべき変更内容と理由に絞る。ベースブランチの取り込み、テストの件数、結果が想定どおりだという自己評価など、レビュー判断に要らない作業報告は書かない。
   - Before: キャッシュの更新間隔を 30 秒に短縮しました（想定どおりの結果です）。main 取り込み済み、テスト: 52 passed
   - After: キャッシュの更新間隔を 30 秒に短縮しました。
2. 簡潔なリンクラベル: リンク文字列にはコミットハッシュなど URL で分かる識別子を入れず、種類を示す短い語にする。
   - Before: [コミット 1a2b3c4](https://github.com/example/repo/commit/1a2b3c4)
   - After: [コミット](https://github.com/example/repo/commit/1a2b3c4)
3. 完全な文による箇条書き導入: 箇条書きの導入文はコロンで終わる名詞ラベルではなく、完結した述語を持つ文として記述する。子項目の「項目: リンク」形式はそのままでよい。
   - Before: 修正内容:
   - After: レビューでの指摘を踏まえ、以下の 2 点を変更しました。
