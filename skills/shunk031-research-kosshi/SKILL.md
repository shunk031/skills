# 簡潔骨子文体

- 最初に必ず `shunk031-research-structured-bullet-writing` skill を読み、使う。
  - その skill が、論点階層・事実保持・不足情報・引用位置を整える。
  - この skill は、その後の表現を短く締める層だけを担当する。
  - 構造作りを省かない。構造ルールをここへ重複して書き足さない。
- 出力言語は日本語を既定にする。
  - ユーザーが別言語を明確に選んだ場合だけ、その言語で書く。
  - 固有名詞、論文名、資料名、モデル名、データセット名、引用文は原文の表記を保つ。
- 対象は任意領域の内容であり、技術発表や振り返りだけに限らない。
  - 社内メモ、調査メモ、提案、レビュー、意思決定メモ、研究ノートなどに使える。
  - 視覚デザイン、スライド構成、PowerPoint/PPTX 生成、配色、タイポグラフィ、画像処理は扱わない。

## 書き方

- 見出しは任意。短い見出しが読みを助ける場合だけ置く。
- 1 つの bullet には、1 つの命題・観察・比較・行動だけを書く。
  - 混ざる場合は分ける。
  - ただし分けすぎて羅列になるなら、上位 bullet を少し太くする。
- 通常はトップレベル 3〜6 本、下位は最大 1 階層。
  - 内容が少ない、または多い場合は数に合わせない。
  - 深い階層で説明を押し込まず、必要なら短い段落を選ぶ。
- 文末は簡潔にする。
  - 体言止め、用言の短い終止、助詞で閉じる断片を自然な範囲で使う。
  - すべてを丁寧な完全文にしない。
  - すべてを体言止めにもしない。局所の文法をそろえる。
- 並列は局所でそろえる。
  - 同じまとまりでは、名詞句なら名詞句、動詞なら動詞に寄せる。
  - 粒度、時制、主語をむやみに揺らさない。
- 順序が自然なら、文脈 → 問題・差分 → 試行・方法 → 結果 → 学び・次を使う。
  - 素材がその順序でない場合も、読者が判断しやすい流れに並べ替える。
  - ただし素材にない因果や結論は足さない。
- 人の声は少し残す。
  - 判断、迷い、次の一手は短く出してよい。
  - 雑談、長い前置き、チャット調の説明段落は置かない。
- 記号は構造のためだけに使う。
  - `➜` は変化、`vs.` は対比、`:` はラベルと中身、`/` は近い選択肢や併記に使う。
  - 便利でも連発しない。
- 箇条書きは Markdown の `-` を使う。
  - 特殊な丸印や装飾記号を要求しない。
  - 太字、絵文字、装飾的な区切り線で短さを演出しない。

## 引用

- 入力にある引用、注、URL は保つ。
- 引用は、それが支える最小のテキスト単位に置く。
  - 方法・モデル・データセット・組織・製品など、引用が特定対象を支える場合は対象名の直後へ置く。
  - bullet 全体を 1 つの出典が支える場合だけ、bullet 末尾へ置く。
  - 比較では、比較対象それぞれに出典を付ける。
  - 長い URL や出典注が bullet を壊す場合だけ、近くの脚注へ逃がす。
- 普通の引用を遠い参考文献セクションへ集めない。
- 出典のない解釈は、`推論:` または `示唆:` と明示する。
- ユーザーが調査や最新確認を求めた場合だけ Web を見る。単なる文体変換ではブラウズしない。

## 手順

- まず `shunk031-research-structured-bullet-writing` skill で、素材を論点と支えに整理する。
- 次に、各 bullet を短くする。
  - 主語、年月、数字、根拠、未決事項を落とさない。
  - 同じ意味を言い換えているだけの語を削る。
  - 形容詞や副詞は、判断に効くものだけ残す。
- 最後に上から読む。
  - トップレベルだけで流れが通るか。
  - 下位 bullet が上位 bullet を支えているか。
  - 引用が近く、解釈が事実に見えていないか。

## 例

入力:

```markdown
4月から試した問い合わせ分類の自動化では、まずFAQ更新の優先度を決めることを目的にした。対象はサポート窓口の問い合わせ1,240件[集計A]で、カテゴリ付与の一致率は人手確認で78%だった。分類に迷った問い合わせは「契約変更」と「料金確認」の境界に集中していた。6月にはラベル定義を見直し、一致率は86%[再評価B]に上がったが、確認作業は週2時間残っている。担当者は、完全自動化よりもFAQ更新候補の発見に使う方が現実的だと見ている。
```

構造化だけ:

```markdown
- 問い合わせ分類の自動化は、FAQ更新の優先度決定を目的として試行された。
  - 対象はサポート窓口の問い合わせ1,240件[集計A]だった。
  - 初期のカテゴリ付与一致率は、人手確認で78%だった。
- 分類の主な課題は、「契約変更」と「料金確認」の境界に集中していた。
  - 6月にラベル定義を見直した。
  - 見直し後の一致率は86%[再評価B]に上がった。
- 現時点では、完全自動化よりFAQ更新候補の発見に使う方が現実的だと考えられる。
  - 確認作業は週2時間残っている。
  - 示唆: 担当者は、運用支援として使う方が現実的だと見ている。
```

簡潔骨子文体:

```markdown
- 目的は FAQ 更新の優先度決定。
  - 対象は問い合わせ1,240件[集計A]、初期一致率は78%。
- ボトルネックは「契約変更」vs.「料金確認」の境界。
  - 6月のラベル再定義 ➜ 一致率86%[再評価B]。
- 当面は完全自動化より、FAQ更新候補の発見。
  - 確認作業は週2時間残存。
  - 示唆: 運用支援として使う方が現実的。
```
