# レトロスペクティブ文体

- 最初に `shunk031-writing-kosshi` skill を読み、骨子を作る
  - 論点の階層、事実保持、引用、不足情報の扱いは同 skill に委ねる
  - この skill は、振り返りや技術発表に合う流れと表現だけを加える
- 内容に合う範囲で、文脈 → 問題・差分 → 試行・方法 → 結果 → 学び・次の順に並べる
  - すべての段階を無理に埋めない
  - 結果が出ていない場合は、途中経過や残った問いとして示す
- 各 bullet は短い日本語で締め、末尾に `。` を付けない
  - 一つの bullet には、一つの観察、比較、判断、行動だけを書く
  - 体言止め、短い終止形、助詞で閉じる断片を自然な範囲で混ぜる
  - 事実、数値、固有名詞、不確実性は短さのために落とさない
- 書き手の判断や迷いを少し残す
  - 成功談へ整えすぎず、想定との差、うまくいかなかった点、判断を保留する理由も書く
  - 学びや次の一手は、素材から言える範囲に限る
- 記号は関係を一目で示せる場合だけ使う
  - `➜` は変化、`vs.` は対比、`:` は短いラベル、`/` は近い選択肢や併記に使う
  - 記号を連発せず、普通の日本語の方が読みやすければ使わない

## 例

入力:

```markdown
問い合わせ分類を自動化し、FAQ 更新の優先度を決めようとした。初期の一致率は 78%で、「契約変更」と「料金確認」の境界で誤りが多かった。ラベル定義を見直すと一致率は 86%まで上がったが、週 2 時間の確認作業は残った。完全自動化より、FAQ 更新候補を見つける用途が現実的だと考えている。
```

出力:

```markdown
- 目的は FAQ 更新の優先度決定
- ボトルネックは「契約変更」vs.「料金確認」の境界
- ラベル定義の見直し ➜ 一致率 78%から 86%へ
- 週 2 時間の確認作業は残存
- 当面は完全自動化より、FAQ 更新候補の発見に使う
```
